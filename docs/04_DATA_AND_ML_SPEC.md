# Data Engineering and ML Specification

## 1. Goal
Build a reproducible pipeline for historical air temperature and experimentally validated +24h/+48h predictions over supported Indian grid cells. Do not claim forecast quality until the inference-time information problem is solved and tested.

## 2. Primary source
ERA5-Land is the initial candidate for historical gridded data. Verify current documentation, access terms, variable availability, temporal resolution, native grid, and data license before implementing a downloader. Use a small sample first.

Candidate variables, subject to source availability and suitability:
- 2 m air temperature: primary target and lag feature.
- 2 m dewpoint temperature or a defensibly derived humidity variable.
- 10 m wind components or speed.
- total precipitation.
- surface solar radiation/related radiation variable.
- surface pressure if useful.
- elevation/static geographic features if available.

Do not assume every candidate variable is included in every downloaded subset. Record exact source variable names and units.

## 3. Data manifest
Every source dataset must have a manifest with:
- source/provider and dataset identifier;
- access URL or retrieval procedure;
- retrieval date;
- license/terms and attribution;
- geographic bounding box and CRS;
- temporal coverage and resolution;
- variable names, source units, transformed units;
- native grid spacing and actual grid coordinates;
- missingness and quality checks;
- checksum/file inventory;
- transformation code version.

## 4. Unit and quality rules
- Convert Kelvin to Celsius explicitly: `C = K - 273.15` where the source unit is Kelvin.
- Confirm precipitation accumulation units and time semantics before conversion.
- Confirm radiation units and whether values are accumulated or instantaneous.
- Preserve UTC timestamps internally.
- Detect duplicate timestamps, non-monotonic time indexes, unexpected grid changes, impossible values, and missing intervals.
- Never replace missing values with zero without a physically justified rule.
- Do not interpolate across long gaps silently.
- Preserve source value and derived value metadata where practical.

## 5. Data split
Use chronological train/validation/test windows. Pick dates only after checking data availability and season coverage. Document exact date boundaries and ensure no future observations influence training features.

Example strategy (illustrative, must be adapted to available data):
- earliest ~70% of time: train;
- next ~15%: validation;
- latest ~15%: test.
The split must be by target date/time, not by random rows. Consider a gap/embargo where overlapping windows could leak information.

## 6. Forecast target
For each grid cell and initialization time `t`:
- `target_t24 = air_temperature(cell, t + 24 hours)`
- `target_t48 = air_temperature(cell, t + 48 hours)`

Train separate estimators per horizon initially. Validate the target alignment with unit tests using a tiny synthetic dataset.

## 7. Candidate features
Only include features available at initialization time:
- latitude, longitude;
- elevation/static region features if reliable;
- hour-of-day and day-of-year encoded cyclically;
- temperature lags (e.g. t, t-1h, t-3h, t-6h, t-12h, t-24h);
- lagged humidity/dewpoint;
- lagged wind;
- lagged precipitation and radiation;
- rolling means/max/min computed only over past windows;
- optional neighboring-cell lagged temperatures if spatial feature design is documented.

Do not use future observed values as features. A variable from a future timestamp is forbidden unless it is generated by a separately trained HeatSense component and the recursive/forecasting design is explicitly evaluated.

## 8. Critical operational forecasting gate
Historical reanalysis labels can train a mapping from recent weather state to future temperature, but a static one-step regressor cannot automatically know future atmospheric forcing. A naive 48-hour model based only on current/lagged weather may be weak.

Before accepting operational prediction:
1. Define exactly what is available at initialization time.
2. Implement the candidate inference strategy (for example, recursively predicting intermediate temperature state; this is a hypothesis, not a guarantee).
3. Compare against persistence and seasonal/time-of-day baselines.
4. Evaluate +24h and +48h on held-out periods, seasons, and regional subsets.
5. Assess forecast drift and physically implausible outputs.
6. If performance is inadequate, stop and report it. Do not hide the issue by importing an external forecast as a silent feature.

Any additional exogenous future inputs must be explicitly approved by the owner and documented. The user's current product requirement is that displayed forecast temperatures come from HeatSense-trained models only.

## 9. Baselines and candidate models
- Persistence: future temperature equals latest available temperature.
- Seasonal/time-of-day baseline where appropriate.
- RandomForestRegressor with controlled tree count/depth and fixed random seed.
- XGBoost regressor with validation-based hyperparameter selection.
- Optional linear regression or HistGradientBoosting as a cheap benchmark.

Keep hyperparameter search bounded and reproducible. Do not use deep learning just for appearance. Add LSTM/temporal neural models only if data volume and evaluation justify the extra complexity.

## 10. Metrics and reporting
For each horizon, report:
- MAE in °C;
- RMSE in °C;
- optional bias/mean error;
- baseline metrics and improvement over baseline;
- per-region and seasonal slices;
- count of valid samples and grid cells;
- test period and data version;
- model configuration and random seed.

Report errors by hot-temperature subset as well as overall performance. Do not use training metrics as proof of generalization.

## 11. Spatial evaluation
- Avoid leakage from the same target timestamp being split across train and test.
- Report geographic coverage and station availability.
- Evaluate at grid-cell level and, where appropriate, aggregated region level.
- If using station observations, distinguish station validation from reanalysis-label evaluation.
- Do not imply station validation covers areas without stations.

## 12. Artifact format
Save:
- model file;
- feature schema and ordering;
- preprocessing parameters;
- horizon;
- training configuration;
- data manifest/version;
- code revision;
- train/validation/test time ranges;
- evaluation metrics;
- library versions;
- known limitations;
- inference input requirements.

Load artifacts with a versioned predictor interface. Fail closed if feature schema mismatches.

## 13. Heat-risk layer
Temperature prediction and risk classification are separate.
- Define whether risk uses air temperature, heat index, apparent temperature, or a recognized local methodology.
- Only compute heat index if required input variables and validated formula are available.
- Document thresholds and jurisdiction.
- Do not call temperature alone a complete health-risk measure.
- Do not issue medical advice or imply official warnings.
- Provide a separate legend and method note.

## 14. Data-size strategy
Start with a small spatial/time pilot. Estimate disk, RAM, and download time before scaling. Use chunked reading and lazy array operations where useful. Avoid converting a multi-year national grid into one giant in-memory DataFrame. Use reproducible config for region, time window, variables, and chunking.
