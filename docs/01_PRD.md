# Product Requirements Document (PRD)
## HeatSense: Predictive Analytics for Heat Risk

**Status:** Baseline specification for implementation  
**Initial geography:** India  
**Expansion path:** Global coverage after data, model, and performance validation  
**Primary users:** General public, students/researchers, urban planners, analysts, and people exploring heat patterns  
**Product type:** Web application combining geospatial visualization, historical analytics, and ML predictions

## 1. Vision
Build a credible, interactive heat intelligence platform that lets users explore historical temperature patterns and HeatSense-trained +24-hour and +48-hour temperature predictions on a geographic map. The experience should feel polished and responsive, including smooth animated navigation from the global view to country, state, and city areas.

## 2. Problem statement
Weather information is often presented as a point forecast or a static chart. HeatSense aims to connect historical temperature context, spatial patterns, and short-horizon model predictions in one interface. The application must be transparent about data sources, grid resolution, forecast uncertainty, and model limitations.

## 3. Product goals
1. Show a navigable map experience with an India-first data coverage strategy.
2. Allow users to search for and select supported geographic areas.
3. Animate camera movement to selected locations rather than abruptly switching views.
4. Render historical air-temperature data and model-produced forecast layers.
5. Provide +24h and +48h predictions for supported grid cells.
6. Show historical time series and regional summaries.
7. Train and evaluate multiple ML models, select models based on held-out performance, and expose model metadata.
8. Make the system reproducible, testable, and modular enough for an AI agent team to develop safely.
9. Prepare interfaces and data abstractions for later global expansion.

## 4. Non-goals for initial release
- Street-level or building-level temperature accuracy.
- Medical advice or guaranteed health-risk alerts.
- Replacing official weather warning services.
- Claiming global forecast coverage while only India is supported.
- Using external forecast outputs as silent replacements for HeatSense model outputs.
- Training models in response to normal web requests.
- Real-time sensor ingestion unless explicitly added as a later scope item.
- User accounts, social features, or complex billing infrastructure.

## 5. Personas and user journeys
### Persona A: Curious user
- Opens HeatSense.
- Sees the global globe or India overview with a clear legend and data timestamp.
- Searches “Mumbai”.
- Watches the globe camera fly to the selected city.
- Selects historical, +24h, or +48h layer.
- Clicks a grid cell to see coordinates, temperature, valid time, horizon, and source/model.

### Persona B: Student/researcher
- Selects a state or city.
- Reviews historical temperature charts and summary statistics.
- Compares model performance and forecast horizons.
- Reads model and data limitations.

### Persona C: Planner/analyst
- Views regional heat distribution.
- Uses boundaries and grid-cell values to compare areas.
- Exports or inspects data only if export is implemented and documented.

## 6. Functional requirements
### FR-01: Map navigation
- Display a geographic map/globe.
- Support pan, zoom, rotate where supported, and return-to-overview.
- Search locations and select supported results.
- Smoothly animate camera flight to selected country/state/city.
- Prevent conflicting flights; a new selection must cancel or supersede the previous transition.
- Respect reduced-motion preferences with a reduced or instant transition.
- Show a loading state when geographic or temperature data is being fetched.

### FR-02: Geographic coverage
- India is the initial production coverage target.
- Coverage must be explicit in the UI and API.
- Unsupported regions must not display fabricated temperature values.
- Architecture must separate location lookup/boundaries from weather grid data.

### FR-03: Temperature layers
- Historical layer: actual selected dataset values, correctly labeled as observations or reanalysis estimates.
- Forecast +24h: values generated by the deployed HeatSense model pipeline.
- Forecast +48h: values generated by the deployed HeatSense model pipeline.
- Legend must show units (°C), range, timestamp, and layer type.
- Missing grid cells must be visibly missing, not assigned arbitrary zeros.
- Color scales must be consistent enough to compare time layers; any auto-scaling must be communicated.

### FR-04: Location search and selection
- Search by city, state, and country where supported.
- Search result includes canonical name, admin region, country, and approximate coordinates.
- Clicking a result triggers animated navigation and updates the selected-region context.
- Handle ambiguous names with disambiguating labels.
- Include a clear selection reset/back-to-overview action.

### FR-05: Historical analytics
- Show time-series chart for selected location/grid cell or regional aggregation.
- Show daily maximum/minimum only if derived from adequate temporal data.
- State whether values are hourly, daily, aggregated, observed, or reanalysis.
- Avoid misleading comparisons across different resolutions or sources.

### FR-06: ML predictions
- Support +24h and +48h horizons.
- Every prediction response identifies model name/version, initialization time, target time, units, input data time range, and coverage.
- Model errors and missing input data return explicit errors.
- Do not claim confidence intervals unless calibrated uncertainty is implemented and evaluated.
- Forecast values must be generated by HeatSense-trained model(s), per project scope.

### FR-07: Model transparency
- Display model evaluation metrics from saved evaluation artifacts.
- Separate validation/test metrics from live prediction outputs.
- Metrics must be reproducible and linked to model/data versions.
- Do not hard-code impressive or invented metrics.

### FR-08: Accessibility and responsive design
- Support desktop and tablet layouts; mobile should remain usable.
- Keyboard-accessible search and layer controls.
- Color is not the sole indicator of data status.
- Reduced-motion support.
- Adequate contrast, visible focus, descriptive labels, and accessible chart summaries.

### FR-09: Operational behavior
- Provide health endpoint.
- Log errors without leaking secrets or sensitive data.
- Cache stable query outputs with correct invalidation by model/data version.
- Avoid reloading model artifacts for every request.
- Keep data preparation and model training out of request handlers.

## 7. Non-functional requirements
- Correctness and provenance take priority over visual polish.
- Reproducible data preparation and training.
- API schema validation and typed frontend API models.
- Graceful empty/loading/error states.
- Reasonable performance for map navigation and grid layer changes.
- Automated unit, integration, and browser tests.
- Configuration via environment variables/config files.
- No secrets committed to repository.
- Logs and errors should be actionable.
- Clear licensing and attribution for basemaps, boundaries, and data sources.

## 8. MVP acceptance criteria
1. A user can launch the app locally using documented commands.
2. The map loads without console errors and identifies the supported coverage.
3. Search for a supported Indian city triggers a visible camera flight.
4. Repeated/rapid location selections do not leave the map stuck.
5. A supported region displays a real historical data layer with timestamp and source.
6. +24h and +48h layers are generated from saved HeatSense model artifacts.
7. Missing data are represented as missing and explained.
8. A grid-cell click displays a value and full temporal/model metadata.
9. A selected location has a historical chart.
10. A chronological evaluation report compares baseline, Random Forest, and XGBoost.
11. API and frontend tests pass.
12. Data provenance, limitations, and setup steps are documented.

## 9. Product risks
- Large weather data downloads and preprocessing can exceed local disk/RAM.
- Historical reanalysis may not yield an operationally skillful forecast without future atmospheric information.
- Geographic coverage and station access can be uneven.
- 3D globe rendering may depend on a basemap/terrain provider, credentials, terms, and network access.
- A coarse grid cannot justify street-level claims.
- A visually compelling heat map can be misleading without a truthful legend and timestamps.

## 10. Decisions to preserve
- India first, global expansion later.
- Own trained ML models generate displayed forecasts.
- Detailed regional grid maps.
- Animated camera flights to country/state/city.
- React + TypeScript, FastAPI, Python ML.
- Start with architecture and repository setup, then a small data feasibility pilot.
- No fabricated metrics, values, coverage, or uncertainty.
